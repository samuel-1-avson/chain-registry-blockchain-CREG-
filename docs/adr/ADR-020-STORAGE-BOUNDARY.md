# ADR-020: Storage boundary — consensus state versus operational state

- **Context/problem:** CREG persists state in two engines and the split has never been written down. Consensus state (blocks, packages, namespaces, transparency log, reorg journal, finalized work) is written by validators and must replay deterministically from identical bytes. Off-chain services (faucet, relayer, L1 hot-wallet signer, indexer) need shared, concurrent, transactional state that survives restarts and is safe across multiple processes. One engine serves neither purpose: putting a server database in the consensus path makes finality depend on a network service, and an embedded key-value store cannot provide cross-process writer leases, SQL aggregation, or paginated public queries.
- **Options:** one server database for all state; one embedded store for all state; SQLite for the off-chain services; embedded consensus store plus a relational store confined to off-chain services.
- **Decision:** adopt a hard boundary. (1) RocksDB is the **only** source of truth for consensus state, opened single-writer by the node process; a complete node state is a directory plus its cursors, and that is the unit of snapshot, restore and rollback. (2) PostgreSQL holds **operational** state only, and every table in it must be reconstructible from chain data or expendable without loss of correctness. (3) No crate on the consensus path may link a Postgres client; adding one requires a superseding ADR.
- **Scope of operational state:** faucet — rate limits, claim ledger, canonical transfer set, funding ledger, reconciliation watermark, PoW redemptions; relayer — metadata, checkpoints, batches, outbox; `l1-tx` — nonce ledger plus writer lease (the lease is the reason this state must be relational rather than local: two signers must never allocate the same nonce); indexer — a derived read model serving `/v1/index/*`.
- **Security implications:** the blast radii are separate. A Postgres compromise cannot rewrite chain history; a chain-state compromise cannot rewrite rate limits or the claim ledger. Operational stores are treated as untrusted inputs to consensus-adjacent flows and are reconciled against chain data (the faucet watermark does exactly this) rather than trusted.
- **Operational implications:** Postgres unavailability degrades the services that depend on it and never blocks block production or finality — observed on 2026-11-26, when a gateway `429` disabled faucet token claims while the chain kept finalizing. That is the intended blast radius, but it is a user-visible availability dependency, so failure handling in those services is held to a higher standard than "the chain is fine" (see the open item below).
- **Migration implications:** the two stores version independently — Postgres through `sqlx` migrations, RocksDB through column-family additions. Column-family additions are **one-way**: a data directory opened by a newer binary cannot subsequently be opened by an older one (`Column families not opened`), and a newer binary may refuse to rewrite a legacy block body that disagrees with its canonical payload. Any node image upgrade therefore requires a verified snapshot, and in-place upgrade is not currently supported for existing data directories.
- **Rejected alternatives:** all-Postgres — consensus determinism would depend on a network service and on MVCC/version behaviour, and replay would no longer be a pure function of bytes; all-RocksDB — no cross-process lease (double-signing risk), no SQL read models, no paginated public query surface; SQLite for the services — no safe concurrent multi-process writers, which is precisely what the nonce ledger needs.
- **Revisit conditions:** state-sync or snapshot distribution lands (weakens the "one-way upgrade" consequence); the indexer is replaced by client-side light verification; or any consensus-path component needs state shared across nodes.
- **In-repo slice (2026-11-26):**
  - Consensus store: `crates/node/src/chain_store.rs`, 19 column families (`blocks_by_hash`, `blocks_by_height`, `packages`, `namespace_*`, `publisher_*`, `transparency_events|leaves|heads`, `reorg_journal`, `finalized_work`, `package_status_v1`, `meta`).
  - Operational store: `crates/l1-tx/src/pg.rs` (nonce ledger; connection policy per `ECA-32` — TLS or a local socket), `crates/relayer/src/store.rs` (4 tables), `crates/faucet/src/main.rs` (6 tables), `migrations/` 001–004 (applied by the indexer through `sqlx::migrate!` in `crates/indexer/src/lib.rs`).
  - Boundary check a reviewer can re-run: `grep -lE 'sqlx|tokio-postgres' crates/*/Cargo.toml` returns `faucet`, `indexer`, `l1-tx`, `relayer` and **not** `consensus`, `validator`, `node`.
  - Open item: the faucet reconciler does not retry after a failed pass (no backoff on `429`), so a transient gateway error disables token claims until the container is restarted. This violates the availability expectation set above and is tracked as a defect, not accepted behaviour.
- **Related:** ADR-011 (retention and durability evidence), ADR-019 (ecosystem services that own the operational stores), ADR-014 (reproducible builds — the snapshot/rollback discipline here is what makes rebuilds verifiable).
