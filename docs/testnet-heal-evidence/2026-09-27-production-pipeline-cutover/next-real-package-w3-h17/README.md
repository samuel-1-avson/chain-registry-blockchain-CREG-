## What failed and what was repaired

The genuine `npm:has-flag@5.0.1` publish reached four validator votes, but V2 alone initially finalized h17. The other seven nodes had no configured HTTP sync path to V2, and the cross-project V2 API port was blocked. The h17 block and three-signature certificate were valid; the problem was the candidate fleet's peer topology. The browser's 15-minute publish event capture consequently timed out before `package_verified` and `block_produced`, while the attached CLI eventually received the verified event. Preserve [the failed browser capture](browser-r13-publish.json) as a failed acceptance result.

I added the narrowly scoped `creg-r7-candidate-sync-from-fiffi` firewall rule for the four existing fiffi VM public `/32` addresses, restored V3 with a direct V2 sync peer, and then added direct V2 peers to V4 and O1–O4 while preserving their containers, identity, storage and signer journals. O1/O2 use V2's private address; the cross-project machines use its restricted public address. V3's first restart command had a Docker argument error after its old container was preserved; I corrected the helper and restarted V3 with the same pinned image, data, identity and journal before continuing. The [post-repair h17 fleet capture](h17-fleet-after-peer-repair-20260928T0253Z.json) shows all eight healthy at hash `7c3364858873b00dcb8eef4875c2f1eaa85ade32648850177bd12dcb5f7627d7`, with clear active work and PBFT rounds. The [h17 certificate](h17-v1-certificate.json) has three valid authorized COMMIT signatures, and the [Linux CLI proof check](cli-r13-positive-proof.log) verifies the real package's Merkle inclusion against the signed R7 spec.

## Real h18 revocation and V4 capture limit

With V4 armed and the browser/CLI watchers attached, the owner-signed revoke was accepted once and finalized at h18, hash `ec64471b8f9c58eb2d9b958db765a98871cb444e032143d313d65b3ab80cd76c`. The [browser capture](browser-r13-revoke-h18.json) passed named revoke, block event, rendered text and no page errors; the [CLI watcher](cli-r13-watch-through-revoke.log) rendered the revoke. The [h18 certificate](h18-v1-certificate.json) has three valid authorized COMMIT signatures. The [post-disarm fleet capture](h18-fleet-after-v4-disarm-20260928T0308Z.json) shows all four validators and four observers healthy and finalized on that same hash, with clear active work and PBFT rounds.

V4 did persist a matching local COMMIT, then logged the exact capture pause. The monitor's buffered log reader delivered the pause line roughly 30 seconds late. Its SIGKILL began **2.415 ms after the pause had resumed**, so this run does **not** prove a crash before local block application. Docker also did not automatically restart a manually killed container under its `unless-stopped` policy. I manually started the same V4 container, and its startup log shows the matching durable COMMIT recovered before P2P and sync services started. The [read-only replay witness](v4-manual-replay-r13-h18.json) proves that narrower observation; the [boundary assessment](v4-h18-boundary-assessment.json) supersedes any interpretation of its `passed` field as full W3 acceptance. The original [monitor report](v4-capture-monitor-r13-h18.json), [arm report](v4-arm-r13-h18.json) and [disarm report](v4-disarm-r13-h18.json) remain intact. The disarm report's `replay_unproven` result is the old helper's conservative outcome because it required Docker's restart count to increase; the independent replay witness records the actual startup marker. W3 remains **open**.

The capture helper now drains log lines through a reader thread, refuses a SIGKILL after the 20-second safety window, explicitly starts the same container after a successful kill, and uses its `StartedAt` change to detect recovery. These code changes have been syntax checked; a future real transaction is required to prove the corrected pre-application boundary.
